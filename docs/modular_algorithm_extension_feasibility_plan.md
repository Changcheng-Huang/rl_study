# 模块化算法扩展功能：可行性验证开发计划

> 第二版 MVP 已按本文档的可行性范围实现。运行和验收说明见
> [`v2_mvp_guide.md`](v2_mvp_guide.md)。

## 1. 文档目的

本文档用于规划强化学习教学平台的模块化算法扩展功能。

当前阶段的首要任务不是直接建设完整的生产系统，而是：

> **通过开发最小可运行代码，验证“新算法资料导入 → 内容生成 → 分模块审查 → 安装注册 → 网站展示与运行”这一完整流程在现有项目中是否可行。**

本阶段应优先得到可以实际运行、测试和演示的代码结果。复杂的多 Agent 协作、生产级安全沙箱、完整权限系统和大规模内容生产将在可行性得到确认后再逐步建设。

---

## 2. 背景

现有平台已经包含四类算法教学模块：

- Animation：展示算法动画、公式、说明和推导内容；
- Theory：展示概念、数学公式、伪代码和测验；
- Jupyter Notebooks：展示和下载可执行 Notebook；
- RL Laboratory：运行算法实验并展示训练指标与可视化结果。

当前项目也已经具备初步的算法包机制，包括：

- 使用 `manifest.json` 描述算法；
- 将 `theory.md`、`notebook.ipynb`、`animation.mp4` 和 `experiment.py` 组织为 ZIP；
- 校验算法包结构和文件类型；
- 安装算法包；
- 将导入内容注册到对应的网站模块；
- 删除错误安装的算法包。

这些功能说明模块化扩展已有基础，但目前仍缺少以下关键环节：

- 从新算法资料生成标准化内容；
- 保证各模块使用同一份算法定义；
- 对不同模块分别审查、修改、批准或拒绝；
- 保存资料来源、生成方式、版本和审核记录；
- 在正式安装前完成端到端验证。

---

## 3. 核心设计原则

### 3.1 使用统一的算法定义

不应让 Theory、Notebook、Experiment 和 Animation 分别独立理解同一个算法。

系统应先建立一份统一的 `AlgorithmSpec`，作为该算法的唯一事实来源。其他模块都根据它生成派生内容。

`AlgorithmSpec` 至少应包含：

- 算法 ID、名称、版本和分类；
- 算法目标和适用条件；
- 输入、输出、状态和动作定义；
- 核心公式；
- 主要超参数；
- 伪代码；
- 支持的实验环境；
- 原始论文、官方文档和参考实现；
- 生成工具、生成时间和版本信息。

### 3.2 大模型只生成草稿

大模型或 Agent 可以参与：

- 从论文和资料中提取算法定义；
- 生成理论内容；
- 生成 Notebook；
- 生成实验代码；
- 生成动画分镜和 Manim 脚本；
- 检查不同模块之间是否存在明显矛盾。

但是，大模型生成的内容必须先进入暂存区，不能直接安装到正式平台。

### 3.3 分模块审核

每个模块应当拥有独立状态，例如：

```text
not_generated
→ generating
→ draft
→ validation_failed
→ awaiting_review
→ changes_requested
→ approved
→ installed
```

审核人员可以对每个模块分别执行：

- 保留；
- 在线修改；
- 要求重新生成；
- 拒绝；
- 批准。

### 3.4 先验证闭环，再扩展能力

本阶段只需要证明以下闭环能够工作：

```text
资料输入
→ 生成统一算法定义
→ 生成模块文件
→ 自动校验
→ 人工确认
→ 打包安装
→ 网站识别并运行
```

第一版不追求覆盖所有算法，也不追求完全自动化。

## 4. 当前阶段的主要任务

### 4.1 任务一：建立可运行的 AlgorithmSpec

在现有 `manifest.json` 基础上增加一份统一算法定义，或者将现有 Manifest 升级为新的 Schema。

建议第一版至少支持：

```json
{
  "schema_version": 2,
  "id": "example-algorithm",
  "name": "Example Algorithm",
  "version": "1.0.0",
  "category": "value-based",
  "summary": "A short summary.",
  "sources": [],
  "algorithm": {
    "objective": "",
    "assumptions": [],
    "hyperparameters": {},
    "core_equations": [],
    "pseudocode": [],
    "supported_environments": []
  },
  "modules": {
    "theory": {},
    "notebook": {},
    "experiment": {},
    "animation": {}
  },
  "generation": {},
  "review": {}
}
```

需要开发并验证：

- Schema 解析；
- 必填字段校验；
- 版本兼容；
- 错误信息展示；
- Schema v1 算法包是否仍能正常使用。

### 4.2 任务二：建立算法包暂存区

新增算法不能上传后立即安装，应先解压到暂存区。

建议目录结构：

```text
algorithm_packages/
├── drafts/
├── installed/
├── rejected/
└── .trash/
```

暂存区需要支持：

- 创建新草稿；
- 保存生成的模块文件；
- 读取草稿状态；
- 更新文件和审核状态；
- 删除或归档草稿；
- 批准后原子化移动到 `installed/`。

### 4.3 任务三：实现最小内容生成器

第一版不需要同时实现多个复杂 Agent，可以先实现一个统一生成服务。

输入：

- 算法名称；
- 一份本地 Markdown、TXT 或 PDF 提取文本；
- 可选的参考链接和说明。

输出：

- `algorithm_spec.json`；
- `theory.md`；
- 一个最小 `notebook.ipynb`；
- 一个符合实验接口的 `experiment.py` 草稿。

本任务重点不是保证生成内容已经达到正式教学质量，而是确认：

- 生成内容可以按照标准结构落盘；
- 不同模块能够共享同一个算法 ID 和版本；
- 生成结果能够进入现有校验流程；
- 审核后能够被现有平台加载。

为了降低首期复杂度，可以先使用固定模板或模拟生成器，再接入真实大模型。只要输入输出契约保持一致，之后可以替换生成实现。

### 4.4 任务四：开发分模块审查页面

在现有 `Manage Algorithms` 页面基础上增加草稿审核能力。

第一版页面至少展示：

- 算法基本信息；
- 来源资料；
- Theory 内容；
- Notebook 基本信息；
- Experiment 参数定义；
- 自动校验结果；
- 每个模块的当前状态。

第一版至少支持以下操作：

- 编辑 Theory Markdown；
- 查看 Notebook；
- 查看 Experiment 源码；
- 运行静态校验；
- 将模块标记为“批准”或“需要修改”；
- 所有必需模块批准后执行安装。

第一版可以暂不提供复杂的富文本编辑器，使用文本编辑框和文件预览即可。

### 4.5 任务五：打通安装与模块注册

审核通过后，系统应生成正式算法包并复用现有安装逻辑。

需要确认：

- Theory 自动出现在 Theory 模块；
- Notebook 自动出现在 Jupyter Notebooks 模块；
- Experiment 自动出现在 RL Laboratory；
- 提供 MP4 时自动出现在 Animation；
- 未提供某个可选模块时不会影响其他模块；
- 安装失败不会破坏已有算法；
- 删除或回滚后平台仍能正常运行。

### 4.6 任务六：建立最小自动化测试

本阶段必须以代码和测试结果确认可行性。

至少需要覆盖：

- AlgorithmSpec 解析；
- 缺少必填字段时拒绝；
- 不安全文件路径时拒绝；
- Notebook 格式校验；
- Experiment 接口校验；
- 草稿状态流转；
- 未批准的算法不能安装；
- 批准后的算法能够安装；
- 安装后各模块能够发现算法；
- 错误安装能够恢复或移入回收目录；
- 原有内置算法不受影响。

## 5. 建议的可行性验证样例

建议继续使用 Monte Carlo Control 作为第一条完整验证链路，因为当前仓库中已经存在示例资料。

验证过程：

1. 将 Monte Carlo Control 原始资料导入暂存区；
2. 创建或生成 `AlgorithmSpec`；
3. 根据 AlgorithmSpec 生成 Theory；
4. 生成或复制 Notebook 草稿；
5. 生成符合统一接口的 Experiment；
6. 执行自动校验；
7. 在管理页面中分别审查三个模块；
8. 修改一处 Theory 内容，确认修改能够保存；
9. 批准 Theory、Notebook 和 Experiment；
10. 安装算法包；
11. 验证三个模块均能识别该算法；
12. 运行实验并确认可以返回指标；
13. 删除算法并确认系统恢复到安装前状态。

如果这条链路可以稳定完成，即可初步确认整体方案可行。

---

## 6. 本阶段的验收标准

满足以下条件时，可以认为可行性验证通过：

- 能从一份算法资料创建统一 AlgorithmSpec；
- 能生成至少两个不同模块的草稿内容；
- 生成内容只进入暂存区，不会直接上线；
- 管理人员可以查看和修改草稿；
- 可以分别批准不同模块；
- 未批准内容不能安装；
- 批准后能够生成或安装标准算法包；
- 安装后平台能自动发现新算法；
- 至少一个新实验可以成功运行并返回合法指标；
- 自动化测试通过；
- 整个过程不需要手工修改平台核心路由代码；
- 安装失败不会影响原有算法和模块。

---

## 7. 本阶段暂不作为主要目标的内容

以下内容重要，但不应阻塞第一阶段的代码可行性验证：

- 多个 Agent 并行协作；
- 自动从互联网持续发现新算法；
- 完全自动生成高质量 Manim 动画；
- 无人工参与的自动发布；
- 完整用户和角色权限系统；
- 分布式任务队列；
- 大规模模型调用调度；
- 完整生产级容器沙箱；
- 算法教学效果的正式用户研究；
- 面向第三方开发者的公共插件市场。

这些能力应在验证核心闭环可行后再逐步加入。

## 8. 主要风险

### 8.1 算法内容不一致

如果各模块分别生成内容，可能出现公式、参数和伪代码不一致。

应对方式：所有生成器只能从统一 AlgorithmSpec 读取核心算法定义。

### 8.2 大模型生成错误

大模型可能生成错误公式、不可执行代码或错误引用。

应对方式：生成内容只能作为草稿；必须通过自动测试和人工审核。

### 8.3 导入代码的执行风险

`experiment.py` 属于可执行代码，静态语法校验无法保证安全。

可行性阶段只允许导入可信的本地示例，并增加超时和独立进程执行。正式开放第三方上传前，必须建设更严格的沙箱。

### 8.4 功能范围过大

如果同时实现资料抓取、多 Agent、动画生成、在线编辑和生产沙箱，容易导致第一阶段无法完成。

应对方式：优先完成 Monte Carlo Control 的单条端到端链路。

### 8.5 破坏现有功能

算法注册和页面路由修改可能影响现有算法。

应对方式：保持 Schema v1 兼容，并为内置算法和导入算法建立回归测试。

## 9. 建议开发顺序

### 里程碑一：数据结构和暂存区

- 定义 AlgorithmSpec；
- 增加 Schema 校验；
- 建立草稿目录；
- 实现草稿读取和状态管理；
- 完成相关单元测试。

### 里程碑二：最小生成流程

- 实现模板生成器；
- 从输入资料生成 AlgorithmSpec；
- 生成 Theory 和 Experiment 草稿；
- 保存生成来源和生成记录。

### 里程碑三：审核页面

- 显示草稿算法；
- 预览和编辑模块内容；
- 展示校验结果；
- 支持模块批准和退回修改。

### 里程碑四：安装和集成

- 批准后构建正式算法包；
- 复用现有安装逻辑；
- 验证各模块自动注册；
- 验证删除和恢复。

### 里程碑五：真实大模型接入

- 将模板生成器替换或扩展为大模型生成器；
- 保存模型名称、提示词版本和生成时间；
- 对模型输出执行相同的 Schema 和文件校验；
- 比较模板生成与大模型生成的质量和稳定性。

---

## 10. 最终结论

该模块化扩展方案与现有项目的注册表、目录扫描和算法包机制兼容，具有较高可行性。

当前最重要的工作不是继续扩大设计范围，而是开发一个能够运行的最小实现，确认以下关键判断：

1. 统一 AlgorithmSpec 能否驱动多个模块；
2. 生成内容能否安全地进入暂存区；
3. 管理人员能否修改和分别批准模块；
4. 批准后的内容能否复用现有算法包机制完成安装；
5. 新算法能否在不修改核心路由代码的情况下出现在各个模块；
6. 安装、运行、删除和恢复流程是否稳定。

完成上述代码和测试后，才能基于真实结果决定是否继续投入多 Agent、自动动画生成、生产级沙箱和完整审核系统。
